# Decisions

Each entry is settled unless a later entry replaces it. To change one, propose it in an issue or a
pull request ([CONTRIBUTING.md](../CONTRIBUTING.md)); don't silently deviate. D entries were decided
when they were written; P entries were proposed while building, and each table's heading says
whether they have been accepted. A note in brackets that starts "Later:" says what has changed
since an entry was written.

## 2026-11-10: founding decisions

| # | Topic | Decision |
|---|---|---|
| D1 | Repo | Separate public repo `ctf-flightdeck`. Private solver packs and event data never go in it; a private pack may depend on flightdeck, never the reverse. |
| D2 | Names | Distribution `ctf-flightdeck`, import `ctf_flightdeck`, command `flightdeck`. Never a plain `ctf` package (too generic: it collides with other CTF tooling). Avoid `ctfdeck` as the project name (reads as a CTFd plugin); fine as a command alias. `ctfpilot` is taken. |
| D3 | Language | Python 3.12+ with uv. CTF tooling and players' scripts are Python; L1 plugins load in-process. Plugins may also be subprocesses speaking JSON, so any language works. (Later, changed in M2: no engine loads in-process. Every engine runs as its own process, in its own copy of the handout, and in a container when lanes run in Docker: P8, D17.) |
| D4 | Interface | Terminal UI (Textual). No web UI. |
| D5 | Agent model | Both: (a) flightdeck's own agent loop against model APIs, and (b) orchestrating external agents (claude/codex CLIs, ACP-capable agents). **Phase 1 is (a)**, via an OpenAI-compatible endpoint, tested on OpenRouter. (b) is roadmap. (Later: (b) was built in M2 for the `claude` and `codex` CLIs, P11; ACP is not built.) |
| D6 | Prototype order | M0 = clickable terminal mock with fake data, to agree on look and controls. M1 = thin working slice with real agents. |
| D7 | Solo/team | Both, chosen in config. Team mode means: never work a challenge a teammate solved, don't step on teammates' live boxes, claim challenges. |
| D8 | Lanes | Number of concurrent lanes is a config setting (`max_lanes`). Boards can drop 40+ challenges at once, so the lane list must scroll, stay compact and sort by what needs attention; overflow waits in a queue. |
| D9 | Execution | Config setting `containerized`: true runs every lane in Docker; false runs on the host (many players use a disposable VM). The choice is shown in the console header and checked in pre-flight. (Later: the setting is `[lanes] runtime = "docker"` or `"host"`, or `--docker` or `--host` on `play` and `practice`; `containerized` is only the deck's internal flag.) |
| D10 | Cost display | Per lane: tokens and turns always; dollars when using an API key with known prices. Per-lane caps. |
| D11 | Alerts | Built from the author's real intervention cues (see CONSOLE-SPEC): effort out of proportion to points, activity that ignores what the description hints at, web lanes heading the wrong way, loops, stalls, teammate solved. |
| D12 | License | MIT. Anyone may use, fork or rebuild it. |
| D13 | Release | Developed in private until the mock and a first working slice were done; public from v0.1.0 (2026-11-11). |
| D14 | Timeline | ASAP. Work on private solver packs goes on in parallel and never blocks flightdeck, or the reverse. |
| D15 | Local models | The orchestrator is code, not a model. An optional **local model role** (no API key) may serve small jobs: triage hints from descriptions, the "ignores the hint" detector, lane summaries for escalation, and media helpers (audio transcription, image description). Rules come first; the local model is never required. Candidates to evaluate in M3: Cactus (`pip install cactus-compute`, Apache-2.0, small tool-calling, transcription and vision models; no OpenAI-compatible server per its README, so it needs its own adapter; set `CACTUS_TELEMETRY=0`), and Ollama / llama.cpp / MLX (OpenAI-compatible local servers). Not in M0 or M1. |
| D16 | Console layout | Two views (chosen at the M0 review, 2026-11-10): a **fleet view** (board + every lane, attention-sorted) and a **focus view** for one lane (transcript, files and diffs, chat box). One-key interventions in the fleet; a chat box and slash commands in both. Rounded panels, slanted header, alert chips, plain Unicode only. Details in CONSOLE-SPEC. The five behaviours proposed at that review beyond the two views (a lane kept off a live box a teammate holds, approvals queued per lane, approving more budget at the 80% warning, parked challenges, any approval sorted with the flags) shipped in 0.1.0 and were accepted on 2026-11-11. |

## Proposed in M1 (built; accepted 2026-11-11)

| # | Topic | Proposal |
|---|---|---|
| P1 | Boards that cannot check flags | A folder board without an answers file cannot tell whether a flag is right. Approving a flag then becomes "submit it yourself, then confirm": `a` = accepted (solved), `d` = rejected. |
| P2 | Decline | `d` / `0` / `/decline` says no without killing the lane: a flag is not submitted, the live box stays off limits; declining more budget stops the lane and parks the challenge. |
| P3 | Quick answers | One key answers what a lane needs: `1` approves an approval, `0` declines it; otherwise the most urgent alert's suggestions are numbered. In the focus view only while the chat box is empty. Kill and a bare fork still open their prompts. |
| P4 | Lane network | A Docker lane gets no network unless its challenge lists a live instance (`urls`), so it cannot fetch solutions or reach anything else. Finer egress rules: not built (ROADMAP: a per-origin egress allowlist). (Later, 2026-11-12: built, issue #14. A lane that may reach its instance reaches only that instance: P9.) |
| P5 | Lane image | flightdeck ships a Dockerfile (python3 and common CTF tools) and builds it only when the player runs `flightdeck image build`; it never pulls or builds an image by itself. |
| P6 | Host runtime | Host lanes run as the player: they can read the player's files and same-user processes' environments, including flightdeck's API key. flightdeck says so before every host run and recommends Docker, a VM or a separate low-limit key; it does not pretend to fence it. |
| P7 | Unpriced models | Cost comes from the API (OpenRouter reports it), else the config's price, else it is unknown. A dollar-capped lane whose cost becomes unknown asks once before carrying on without the dollar cap. **Refinement (shipped in 0.1.0; accepted 2026-11-11):** only spend with no price asks. A coding-agent CLI reports a turn's cost when the turn ends, so until then the lane's dollars show as still to come, never as $0.00. A turn whose cost the CLI never reported (an escalation or a kill stopped it in the turn, or it exited) and that no config price covers leaves the lane's total not fully known, but the cap stays and holds on what is known, and the lane says so once. `[prices]` may price a model of an `[agents]` ladder (codex reports no cost), and a CLI's own figure (claude) wins over a config price. |


## Proposed in M2 to M4 (built; accepted 2026-11-11; D17 changes P8)

| # | Topic | Proposal |
|---|---|---|
| P8 | L1 before lanes | With an L1 pack, a lane runs the engines routed to its challenge before its first model call; a flag one finds waits for the player like any candidate, and the model hears what they found (fenced as data). Engines run on the host, as the player, whatever the lanes' runtime: they are the player's own code. |
| P9 | Live instance policy | `auto`: lanes may reach their challenge's instance. `confirm`: a lane asks before its first model call; until the player allows it, its http tool is off and a docker lane has no network, then the container joins the bridge network (open egress, not only the instance). `off`/`manual`: never. On the host runtime only the http tool can be held back (pre-flight warns). (Later, 2026-11-12, issue #14: a docker lane is never on the bridge network. Once it may reach its instance it is on an internal Docker network of its own, with no gateway, and reaches only the hosts and ports its challenge's `urls` name, each through a small proxy container started from the lane image; a coding-agent lane reaches its CLI's API the same way, and L1 engines that run online share such a network per lane. An instance given by IP address or as localhost has a name there, `instance-<address>`, which the lane's brief gives. When Docker cannot build that, the lane gets no network and says why; it never falls back to bridge.) |
| P10 | Known-wrong flags | A flag the platform rejected, or the player declined, is remembered per challenge: proposed again by any lane it raises no approval and is never submitted again, a sibling's waiting approval for it is dropped, and an escalated model hears of it. The platform's rejection outranks a decline. |
| P11 | Coding-agent CLIs | `play --agent claude\|codex` runs lanes as that CLI, with its own key or token and its own model ladder (`[agents]`; claude defaults to sonnet then opus). A docker agent lane needs the CLI in its image and a network for the CLI's API, so an event whose instance policy is not `auto` refuses agent lanes. Files a CLI would read as its own configuration (CLAUDE.md, AGENTS.md, .mcp.json, .claude/, .codex/) are moved out of the workspace first: they are challenge data. A lane waiting for the player is frozen (SIGSTOP) so it spends nothing. |
| P12 | Cactus Needle | An adapter and an optional extra (`ctf-flightdeck[cactus]`), off unless asked for, its telemetry turned off. In a first trial it beat keyword rules only when given the same keywords as triggers (70% against 67% on invented blurbs), so nothing uses it by default. |
| P13 | CTFd answers | CTFd's "already solved" and "locked out" are not a correct flag: flightdeck asks the player (and in team mode "already solved" closes the challenge at once). A flag attempt is never retried. (Later: "already solved" closes the challenge at once in solo mode too, and asks nobody. On "locked out", 0.2.0 closes the challenge as out of tries instead of asking: P18.) |
| P14 | Extras | `[cactus]` (Cactus Needle) and `[build]` (pytest, for `flightdeck build check`) are optional extras, so the default install stays small. |

## 2026-11-11: decisions

| # | Topic | Decision |
|---|---|---|
| D17 | L1 isolation (changes P8) | When lanes run in Docker, the player's L1 solvers run in Docker too (a container per engine run, the pack mounted read-only), so a hostile handout cannot reach the player's machine through a solver's parser. On the host runtime they run as the player, as P8 had it. |
| D18 | Keys | Keys live in the environment or in `~/.config/ctf-flightdeck/keys.env` (owner-only, outside the repository); the config names each key's variable and never holds a key. A variable set in the environment wins over the file. |
| D19 | Model APIs | flightdeck's own lanes may use the Anthropic Messages API directly (the player's Anthropic key first), with an OpenAI-compatible API (OpenRouter) as the automatic fallback when the first keeps failing; a lane that falls back stays there for the rest of its current context. |
| D20 | Autopilot | **Autopilot** is the name of the mode where flightdeck runs an event end to end: scheduled pulls, L1, lanes, interventions and submits, with the player away. It comes after v0.1.0, as M5 (see ROADMAP). Fixed now: the event's rules stay the ceiling (autopilot is never looser than the profile); it never guesses a flag or spends a challenge's last try; engaging it needs a run budget; it disengages, holding the queue and raising an alert, when something needs a human; the player can always take the controls (take over, pause, kill, or switch autopilot off). The rest of its design is decided in M5. |

## Proposed with the light role (shipped in 0.1.0; accepted 2026-11-11)

| # | Topic | Proposal |
|---|---|---|
| P15 | Light role (extends D15) | D15's local model role becomes the light role, `[light]`: `rules` (the default: no model), `openai` (any OpenAI-compatible server; recommended and said so in the docs, `init` and `doctor`: an open-weight model on the player's machine, which no provider classifier can stop and which costs $0), `anthropic` (an API model, which D15 did not allow), `cactus` or `decider` (a Strands Decider server on the player's machine: a decision model that writes no text and picks one of the options with a calibrated confidence). Every engine is measured with `flightdeck eval-local` against the rules before use. Its first job in a run is the hint judge. Nothing waits for it: an "ignores the hint" alert is raised at once by the rules, and a light model's "the lane follows the hint" takes it down (before, the alert was held until the judge confirmed it). A refusal, an error, a timeout, a malformed answer or one outside the options leaves the rules' answer, and the run says so once per kind; a refused request is never rerouted to another model or provider. The decider's answer below `[light] threshold` (0.9 by default) is unsure: neither an answer nor a failure, so the rules' answer stands, and eval-local counts unsure answers apart, neither right nor wrong (its accuracy is over the answers it was sure of). The judge's yes or no goes to it as a choice between two options, read against that confidence (its yes/no question type returns no confidence, and its choices are the type it is calibrated for). It gets one request at a time, as its documentation advises, and the challenge's text only in its state, never in its question. A light model that cannot be made (no key, Cactus missing) leaves the judge off with a note and never stops the run. |
| P16 | Fast mode | `[api] fast` lists the ladder models a lane calls in fast mode, on the Anthropic API only, and only models Anthropic documents fast mode for (Opus 5.5, Fable 5.2, Mythos 5.2; Opus 5 and Opus 4.8 as research previews, Opus 4.8 until 2026-11-30). A fast call is priced at the fast rate. On fast mode's own 429 the lane goes on at standard speed at once and stays there for its session (each switch invalidates the prompt cache), saying so on its transcript. |

## Proposed with the cleanup after a killed run (shipped in 0.1.0; accepted 2026-11-11)

| # | Topic | Proposal |
|---|---|---|
| P17 | Leftovers of a killed flightdeck | When flightdeck itself is killed (SIGKILL, a power loss), what its lanes started can outlive it: lane containers, L1 engines, coding-agent CLIs, servers a lane left in the background. So a run marks what it starts. Its containers carry flightdeck's labels: the run, and the flightdeck that started it (a hash of the machine's id, the user id, the pid, its start time, and its state folder as a hash). Its process groups on this machine are listed in the run folder's `processes.json`, which a note in flightdeck's state folder (`~/.local/state/ctf-flightdeck/open-runs/`, under `$XDG_STATE_HOME` when that is set) names, so the run is found wherever `--run-dir` put its folder; record and note go when the run ends cleanly. `play` and `practice` remove what a run whose flightdeck is gone left running before they start, and say what they removed. `doctor` only reports it, and removes it with `--clean`: doctor is run to look at a setup, often just after something went wrong, and a leftover container may be what the player wants to look into. A recorded group is killed only while a recorded process with the same start time is still in it and works under the run's folder, so a pid the system has given out again is never signalled. Nothing unlabelled, unrecorded or labelled by another state folder is ever signalled or removed. |

## Proposed after the CTFd rehearsal (built in 0.2.0; accepted 2026-11-12)

| # | Topic | Proposal |
|---|---|---|
| P18 | Out of tries (changes P13) | P13 has the deck ask the player on CTFd's "locked out". A rehearsal against CTFd 3.8.9 showed why that is wrong: CTFd checks no more flags for the challenge, so the question "did CTFd accept it?" has no true answer, and a truthful "rejected" recorded a right flag as wrong. Proposed: an answer that says no tries remain closes the challenge as out of tries and asks nobody; the flag is recorded as unchecked, never as wrong. flightdeck asks the challenge's details first, because CTFd 3.8.9 says the same for a burst of tries within a minute, which passes (that case stays a rate limit). A later pull that finds tries again opens the challenge, parked, for the player to queue. "Already solved" stays as P13 has it. |

## Proposed with Autopilot (built in M5; accepted 2026-11-12, P20, P21 and P23 as the maintainer changed them)

D20 fixes the frame; these fill it in. Each is built and tested (`autopilot.py`, `tests/test_autopilot*.py`).

| # | Topic | Proposal |
|---|---|---|
| P19 | Engaging autopilot, and its states | `play --autopilot` (and `practice`), or `[autopilot] engage = true`, engages it when the board is released; `/autopilot on` engages it later, `/autopilot off` takes the controls back. Engaging needs a run budget (`[autopilot] budget_dollars`, `budget_tokens`, or `--budget-dollars`, `--budget-tokens`): without one `play` does not start, and `/autopilot on` is refused, each with the reason in one line. Before lanes start, `play` says what autopilot will and will not do under this run's policies. It has three states. Off: nothing acts. Engaged: its rules act and its guardrails hold. Disengaged: something needed a human, so the rules stopped and the queue is held, but the guardrails still hold, because the player is away. The player touching the controls ends that: their first intervention, `/unhold` or `/autopilot off` turns autopilot off, and it stays off until `/autopilot on`. Every run has an autopilot, off unless asked for. |
| P20 | Never looser, and what it may do | Autopilot changes no policy: every stage runs as the event profile and the config have it, so under submit auto a flag a lane claims is submitted by the deck as without autopilot, and everything else waits (a scraped flag, a handout's own stand-in, a flag the flagcheck holds, every flag under confirm, a live-box request under confirm). Autopilot submits nothing itself and never answers a flag or a live-box request. The deck enforces it: an intervention by autopilot may only escalate, fork, kill, redirect, pause, queue, or approve a budget request (`Deck.apply(by=Actor.AUTOPILOT)`); an answer to a flag, a decline, a take-over or a claim is refused there. The one approval it gives is a lane's own budget request (its per-lane cap), while the run budget has room: the lane's caps go up a step and it carries on, on its model. Small lane caps then let spend creep up a step at a time, and the run budget is the limit that counts. A lane whose spend has no price waits for the player (going on without its dollar cap is theirs to say). (The maintainer, 2026-11-12: approve more budget rather than go up a model.) |
| P21 | The last try | While autopilot guards the run (engaged, or disengaged with the player away), no flag goes to the platform on its own when it would spend the last try the platform counts at a challenge (its count is 1), `submit_limited = "auto"` or not (D21 leaves D20's rule as it is). The gate is in the deck, where every flag passes (`_candidate`, and the line of flags waiting their turn), so no path goes round it. A count the platform has not given is not taken for the last try: such a flag goes out as auto submit sends it (the maintainer, 2026-11-12). When the platform judges a flag wrong without saying what is left, and a count is known, the deck counts that try itself while the guard holds, down to 1 and never to 0 (out of tries is the platform's to say). The flag waits for the player as an approval, which raises the lane's flag alert and a warning for the run; the run goes on, and autopilot stays engaged. A yes the player gave while more tries were left does not carry over to the last one. |
| P22 | The schedule and the next round | An event profile may say `[event] start` and `end`, ISO 8601 times with a zone. Under autopilot a `start` still to come is waited for after every check and before the first pull, saying so (Ctrl-C stops the wait: nothing has started); at the `end` the run stops as quitting does, unless the player has the controls back. An event whose end has passed is refused. New waves are pulled on the existing timer under pull auto. When the queue is dry and no lane is running, each unsolved challenge a lane gave up on, or that a rule parked, is queued on the next model up the ladder, lowest points first, each challenge at most once per rung; when every one has been tried on the top rung autopilot idles until a new wave or the end. A challenge the player parked stays theirs until they queue or fork it. |
| P23 | Interventions by rule | Code decides (D15); no model is asked beyond the light hint judge the Watch already has. A stall alert: the lane is escalated one rung; at the top rung it is killed and its challenge parked. A lane that gave up: its challenge goes round again (P22). A loop alert: the lane is killed and its challenge parked for the next round. An "ignores the hint" alert: the lane is redirected to the alert's own suggestion (the detector's words from flightdeck's tables, never a challenge's), once per lane; a second such alert on that lane waits for the player. A "wrong direction" alert (web): redirected to its suggestion the same way. An "effort vs value" alert: the lane is killed and its challenge parked for the next round, on the next model up, as a loop's is (the maintainer, 2026-11-12). A lane that is paused or taken over, that waits for the player's answer to a flag or a live-box request, or whose flag is on its way to the platform is never touched. |
| P24 | The run budget | In dollars, tokens or both, over every lane's spend (`Deck.totals`). It is checked after every turn and every spend outside a turn. At the budget autopilot holds the queue (no new lane starts), pauses the lanes that run or wait (each finishes the turn it is in; pausing is what stops the spend, since a lane's own cap may be far off or absent) and disengages. It goes on pausing lanes while disengaged, until the player is back. Under a budget in dollars alone, spend with no price cannot be held to it, so that disengages too; with a budget in tokens beside it the run goes on. `/autopilot on` is refused once the budget is spent. |
| P25 | No refused request rerouted | While autopilot guards the run the model client sends no server-side refusal fallback (Anthropic's `fallbacks`), which is the one thing in flightdeck that runs a declined request again on another model; the player's own setting is back when they have the controls. The `[fallback]` API already never takes a call a model declined. A challenge whose lane ended on its model's refusal does not go round again on the next model: it stays parked for the player, and a warning says so. A coding-agent CLI talks to its own API: flightdeck reroutes nothing there and cannot see what the CLI does with a refusal, which the start notes say. |
| P26 | Docker only | Autopilot engages only on the Docker runtime, where a lane reaches its challenge's own instance and nothing else (P9, issue #14). On the host runtime a lane's shell reaches whatever the machine reaches, so `play --autopilot --host` does not start and `/autopilot on` is refused, each saying why. |
| P27 | Disengaging | One function holds the queue, stops the rules and logs a warning whose data is `{"autopilot": "disengaged", "reason": ...}` (what a notifier listens for and the post-flight report lists); the console shows it, and the header says the queue is held and why. Reasons: the run budget reached; spend with no price under a dollar budget; the queue held by anything else (a model API failing for every lane, an outage); the platform failing (the same CTFd poll failing three times in a row), a flag CTFd did not judge (paused, rate-limited, no answer), or a web page where CTFd's API should answer (`HumanCheck`: HTML that is not JSON with a 2xx or 4xx status, 401 and 404 apart; flightdeck does not guess whose page it is and never tries to pass it); the event's end. A challenge down to its last try does not disengage (P21). |
| P28 | Told apart from the player | Autopilot's interventions carry `"by": "autopilot"` in the run log and read as autopilot's in a lane's transcript and every text ("by autopilot; parked"); the player's are logged and worded exactly as before. The post-flight report counts only the player's under Interventions and has an Autopilot section (its interventions, each disengage with its reason, what its guardrails kept for the player); the scorecard and the flight card's steering, verdicts and mode count the player's only, and the card says `autopilot: engaged, N interventions by rule`. |

Left for later: the coding-agent driver does not hold the queue on an API outage (so that never
disengages autopilot there); a headless run must set `Run.stopper` for the event's end to stop it
through its own exit (without one the run shuts itself down); a lane that waits for a live-box
answer keeps its slot until the player is back.

## 2026-11-12: decisions

| # | Topic | Decision |
|---|---|---|
| D21 | Counted tries | When the platform limits the tries at a challenge's flag (CTFd's max attempts), every flag for that challenge waits for the player's approval, under submit auto too. A player who wants a run to go on without them can opt in: `[lanes] submit_limited = "auto"` lets submit auto spend those tries, the last one included. It is off by default, does nothing unless submit is auto and the event's rules allow that, and `flightdeck preflight` and the start of a run say when it is on. D20's rule for Autopilot (it never spends a challenge's last try) is unchanged. |
| D23 | The header's drop order (closes the M0 review) | The five console behaviours proposed at the M0 review are in the spec proper (D16). The header keeps its drop order as built: on a narrow terminal the run's dollars and tokens go before the event's name and the clock. The proposal to rank cost above them is declined for the wide layout; the compact layout (64 columns or fewer) keeps what needs you and the run's dollars instead. |
| D22 | Leaderboard and flight cards (an exception to D1) | The repository holds a public leaderboard, `docs/LEADERBOARD.md`: the events flightdeck was used in, the team's finish, the players' GitHub names, their setup and how hands-on they were (one of three modes: hands-on, approve-only, hands-off). A row comes only from the players themselves, through the leaderboard issue form, after the event has ended and where its rules allowed AI tools; it names only people who agreed, and is removed on request. It never holds a flag, challenge text or a writeup. `flightdeck share` prints a flight card for a run (setup, models, solves by category, time, spend, interventions and the mode) with no flag, challenge name or challenge text in it, and sends nothing: the player pastes it where they choose. flightdeck itself still has no telemetry. Everything else D1 says stands: no real event data in code, tests or fixtures. |

## Proposed with the solver pack (built; not yet accepted)

| # | Topic | Proposal |
|---|---|---|
| P29 | Installing a pack | `flightdeck pack install [SOURCE]` fetches a pack with git (flightdeck's own: the `packs/solvers` folder of this repository at the release's tag, sparse; a source checkout uses its own folder), and acts on its `pack.toml`: a setup command, run on this machine as the player, only after showing it and asking (`--yes`; with no terminal it stops); an image for its engines; `[l1] pack` and `image` written into the config. flightdeck never fetches a pack or runs a setup command by itself. |
| P30 | A pack's own image | `[l1] image` names the image L1 engines run in when lanes run in Docker (D17 holds: a container per engine run, the pack read-only, no network unless the lane may reach its instance, and then only that). The fence's proxies stay on the lane image. A run does not start while the image is missing. |
| P31 | One engine for every challenge | A route may say `any = true`; engines are given the event's flag format (`FLIGHTDECK_FLAG_FORMAT`). The solver pack is one such engine, its whole intake, so its own routing, unpacking and decoy rules decide inside it, and flightdeck's rules for an engine's flag decide what happens to the result. |
| P32 | The pack as the lanes' toolkit | `[l1] lane_tools = true` puts a pack's own note (`[lanes] note` in its `pack.toml`) in every lane's brief, after the challenge's fence and outside it, in the player's name: the player chose the pack, and its author's words are not challenge text. Docker lanes then run in `[l1] image`, with the pack mounted read-only at its own path; their network stays fenced to the challenge's instance. `pack install` turns it on for a pack that brings a note. A pack with no note stops such a run before it starts. |
